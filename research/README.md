# Research Maturity Extensions

Day-one exploration uses the core documents, ordinary code/tests/configuration,
and basic provenance. The directories below are extension points, not active
requirements. Do not add a control merely because the folder exists.

## Maturity path

### Lightweight exploration

Required: clear question, scoped inputs, simple baseline, reproducible command,
proportional tests, evidence entry, and basic provenance. No frozen registration,
protected-data firewall, adversarial attestation, or complete attempt ledger is
required for disposable exploration.

### Candidate promotion

Use `registry/` when an exploratory idea becomes a named candidate. Freeze only
choices capable of changing the conclusion: unit, population, features, controls,
outcomes, exclusions, partitions, preprocessing, evaluation, uncertainty,
multiplicity, and success criteria. Amend rather than overwrite, and disclose
whether outcomes had already been accessed.

### Validation

Before first access to genuinely untouched data, add explicit allowed/prohibited
partitions, a row-free readiness check, exact input/config/code identities, and a
proportional adversarial review under `reviews/`. Full SHA-256 manifests or
numerical contracts are justified only when mutable bytes or analytical degrees of
freedom could change the conclusion.

### High-stakes deployment

Only then consider independent replication, final holdouts, monitoring, rollback,
security, operational audit trails, and separate deployment approval.

## Optional locations

- `registry/`: immutable candidate/experiment registrations.
- `reviews/`: bounded review reports and, only when justified, attestations.
- `results/`: small publishable summaries or pointers to ignored large artifacts.

These locations grant no authority by existing. Protected access and consequential
actions require an adopted decision or explicit user instruction.
